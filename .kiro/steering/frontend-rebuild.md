# Vandy Food Radar frontend rebuild

The user authorized implementation after discussing the feature set. Read
`.kiro/skills/frontend-skill/SKILL.md`; apply its Apps and Utility Copy sections.
Source: https://developers.openai.com/blog/designing-delightful-frontends-with-gpt-5-4
Also reference https://developers.openai.com/api/docs/guides/frontend-prompt
and https://developers.openai.com/plugins/concepts/ui-guidelines.

Visual thesis: a quiet, precise campus workspace with ChatGPT/Codex-like neutral
surfaces, compact controls, disciplined type and restrained Vanderbilt gold.
Use a slim desktop sidebar, a modest working-page heading, unboxed daily brief,
8px event-card radii, fine borders, and no decorative shadow or marketing hero.
The user explicitly rejected the prior cream-colored rounded marketing mockup.
English product UI is consistent with the existing app. Keep explanatory prose
out of the product. Mobile needs its own navigation and reachable 44px targets.

Interaction thesis: cards browse one selected local date, schedule browses the
selected week, map and agenda share selection, and saved activities can be
arranged into an itinerary on a single date. Animate only local interactions
briefly and respect reduced motion.

Preserve Flask, Python repositories, authentication and publication guarantees.
Use Jinja plus maintainable vanilla JavaScript modules instead of introducing a
new application framework/build pipeline for this bounded rewrite.

Deliver all of the following as working behavior:
- Default to TODAY in America/Chicago. Explicit date filtering must never mix days.
- Two-column desktop cards and single-column mobile cards around an 800px breakpoint.
- Card recommendation stars (0-5), time, food, full building name, listed original
  location, RSVP, organizer, inferred participation note, source/detail actions.
  Hide routine partially-verified badges in details but retain cancellation and
  material conflict/time/venue-change warnings. Do not invent source facts.
- Weekly agenda and Leaflet map, event selection/pan, saved markers, and mobile
  agenda/map switch. Lazy-load map. Give an understandable state if it cannot load.
- Local browser storage for bookmarks, origin and itinerary; safely handle corrupt
  storage or blocked storage. Validate restored values.
- Origin combobox backed by the campus dataset, map pin selection, browser GPS,
  and explicit text search submission if supported without public autocomplete abuse.
- Google Calendar prefill link and ICS download (no server credentials required).
  Handle unknown times, overnight ends, timezone/DST, escaping and UTF-8 line folding.
- Grounded daily summary generated by deterministic rules, cached by content
  hash. No new AI credentials, subscriptions or fabricated AI prose.
- A walking endpoint using optional VFR_ORS_API_KEY (server side only); route
  caching, bounded inputs, timeout, and explicit straight-line estimate fallback.
  Keep routing keys out of HTML, logs and URLs. Support only fixed ORS endpoints.
- Itinerary order/manual adjustment, walking segments and feasibility based on
  start/end windows, configurable dwell minutes and departure time. Optimize a
  small selected set with time-window-aware search; don't assert global optimality
  for heuristic results. Exclude cancelled events and unresolved coordinates.
- Resolve location aliases via public/static/campus-places.json. The coordinating
  Codex agent owns this dataset; do not write it. Schema is an array of objects
  {id,name,aliases,lat,lng,source_url}, from Vanderbilt official campus map. Match
  conservatively, preserve room details, unknown locations remain unresolved.
- Participation assessment from description and organizer using explicit evidence;
  explicit eligibility restrictions are warnings, not small scoring penalties.
  Add at most 5% participation convenience influence, explain when inference is
  uncertain. Obtain text from existing source records/full description.
- Fetch/store multiple days: replace_day deletes only stale rows on its day;
  bounded rolling retention; batched refresh with one durable flush after all
  days succeed. Never erase another day during partial refresh. Existing CAS
  publication remains. Allow protected refresh days=2 or days=7, and schedule
  every 2h (near term) and 6h (week), with no concurrent runs and last-success
  metadata. Keep the old API/CLI contracts where practical.
- Meaningful backend tests for selected-date, day isolation, calendar, routing
  validation/estimation and refresh atomicity. Keep tests strict, adapt old tests
  only to intentional default-date/retention changes. Run lint/type/test checks.

Security: escape all activity text, reject javascript/data external URLs,
no unsafe innerHTML with source content, numeric coordinate validation,
no generic proxy endpoints, no raw location claims or fake geographic data.
Do not read secrets, deploy, push, commit, alter cloud services, or change user
account settings. Work only in this repository. Keep offline demos clearly labeled.
Update README with behavior and optional configuration.
