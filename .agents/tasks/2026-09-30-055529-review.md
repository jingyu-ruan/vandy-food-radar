# Vandy Food Radar M1–M6: offline Discover→Display pipeline

The build implements the full MVP pipeline (T1.1–T6.9) as a single modular Python app: SQLite repository, offline source adapters, canonical normalizer, deterministic deduplicator, authority-precedence verifier, transparent weighted-sum ranker, and a server-rendered Flask UI. Stages are threaded by a pipeline orchestrator that upserts idempotently and diffs history. The whole thing runs with no network — a fixture fetcher backs the source adapters and Haversine/Null location providers replace any maps API. The end-to-end fixture test asserts the exact behaviors the spec calls for, and `make check` (ruff/black/mypy/pytest, 93 tests) plus the e2e/web suites all pass on an independent run.

Watch for: nothing blocking. Two minor observations — the `dedup_key`-vs-`identity_key` split means the `Repository.find_by_dedup_key` contract described in FEAT-001 ("upsert by dedup_key") is actually implemented as upsert by `identity_key` (confirmed, deliberate and correct for AC-11); and food-level confirmation is resolved outside the generic per-field cross-check so `food_confirmed` provenance is always `missing` (confirmed, cosmetic).

**Verdict**: APPROVED

## High-level view

Layering matches the design's dependency rules. The web layer reads only through the `Repository` protocol and never calls sources or the ranker directly — it rehydrates persisted `ScoreComponent` rows and re-applies the deterministic §6.2 order for display. Sources, providers, and the HTTP fetcher are all constructor-injected, and `config.offline` defaults to `True` with a `FixtureFetcher`, so every path runs without network.

The ranking engine encodes the §6.1 weight table exactly (0.25/0.25/0.15/0.10/0.05/0.10/0.10, summing to 1.0) with the documented per-factor value derivations, stores a `ScoreComponent` breakdown per factor, and orders by score desc → earlier start → title with cancelled forced last. Weights and thresholds live in config, so re-weighting is a config change.

Persistence is idempotent by a stable `identity_key` (date + title tokens) rather than the full `dedup_key`, which is the crux of AC-11: a verified 18:00→19:00 time change or a venue change updates the same row in place (refreshing its `dedup_key`) and records history, instead of inserting a duplicate. Child rows are replaced inside one transaction on every upsert.

Conflict resolution gathers each source's per-field value, resolves by authority precedence with a recency tie-break, and preserves every losing value on a `Conflict` row. Cancellation from any contributing source overrides all other state and appends exactly one transition history entry, guarded against re-appending on repeat runs.

Known gaps are cosmetic: `food_confirmed` provenance is always `missing` because event-level food confirmation is derived by a dedicated resolver (correct for E-5) rather than the generic field cross-check, and the FEAT-001 note describing upsert "by dedup_key" is stale relative to the shipped `identity_key` keying.

### Layering and offline-by-default injection

The web app (`web/app.py`) is built by a `create_app` factory that takes a `Repository` and optional injected `sources` / `location_provider` / `today_provider`. The index view calls `repository.get_events_for_day`, pairs each event with `repository.get_score_components`, and runs `order_events` to reapply the deterministic §6.2 ordering — the SQL read only orders by score/title, so re-ordering in the view is what keeps cancelled-last and the start-time tie-break honored. It never imports a source adapter or recomputes a score; the scores were persisted at pipeline time. This is the read-only-through-repository rule the design mandates, and it's held.

`config.offline` defaults to `True`, and `default_fetcher` returns a `FixtureFetcher` regardless (a live fetcher is explicitly out of MVP scope), so `build_sources` wires adapters that resolve URLs against the in-repo corpus. `Window.from_config` takes `today` as a parameter rather than reading the clock, so window derivation is pure and the whole pipeline is driveable offline and deterministically in tests.

### §6.1 ranking weights and determinism

`_default_ranking_weights` in `config.py` is the §6.1 table verbatim: food_confirmed 0.25, full_meal 0.25, food_specificity 0.15, rsvp_likelihood 0.10, timing 0.05, walking 0.10, confidence 0.10 — sum 1.0. The engine's per-factor derivations match the design: confirmed/unconfirmed/contradicted → 1.0/0.3/0.0; full_meal ladder 1.0/0.4/0.2/0.0; specificity counts distinct non-generic named food terms at 0.25 each capped at 1.0; RSVP likelihood 1.0/0.7/0.3/0.5; timing is a preference curve with an unknown-time neutral 0.5; walking reads the provider and falls back to `walking_unknown_value` (0.5) on unknown so it never zeroes the score (FR-30/AC-8); confidence passes through the verifier value.

`order_events` sorts on `(cancelled, -score, start_ordinal, title)` with unknown start times ordinal'd to `+inf` (sort last) and cancelled forced to the bottom — the §6.2 contract exactly. Because weights come from config, the "weight change reorders" test is a genuine re-weight rather than a hardcoded expectation.

### Idempotent upsert and the identity_key/dedup_key split

The subtle and correct decision here: `dedup_key` fingerprints the *current* shape of a cluster (date + title tokens + venue + rounded start), while `identity_key` is deliberately narrower (date + title tokens only). The repository's `save_event` does an `INSERT ... ON CONFLICT(identity_key) DO UPDATE`, refreshing `dedup_key` and every mutable field in place, then deletes and re-inserts the event's source records, provenance, conflicts, and score components within one transaction.

```
run 1:  "Spring Gala Dinner" @ 18:00 Hall A
        identity_key = 2025-03-11|dinner gala spring
        dedup_key    = 2025-03-11|dinner gala spring|a hall|1800
run 2:  same event @ 19:00 Hall A   (verified time change, E-2)
        identity_key = 2025-03-11|dinner gala spring     ← unchanged → UPDATE
        dedup_key    = 2025-03-11|dinner gala spring|a hall|1900  ← refreshed
        → one row, start_time updated, start_time history appended
```

This is what makes AC-11/E-2/E-3 work: a time or venue change updates the existing row and logs history, rather than the full `dedup_key` (which includes time+venue) minting a duplicate. The orchestrator adopts the persisted event id when `find_by_identity_key` hits, so history and child rows stay under one stable id. The e2e idempotency test confirms a third run neither duplicates events nor grows the source-record or cancellation-history counts.

One documentation mismatch: FEAT-001's recorded findings still describe `save_event` as "UPSERT by event.dedup_key". The code upserts by `identity_key`. The shipped behavior is the correct one; the note is stale.

### Conflict resolution preserving losers

`resolve_field` (`verify/conflict.py`) gathers present values per field, classifies agreement (agreed / resolved_conflict / single_source / missing), and on disagreement selects the winner by `(authority_rank, -recency, source_id)` — authority precedence first (official_page > anchor_link > google_calendar), most-recent `source_updated_at` (falling back to `checked_at`, noted in the resolution string) as tie-break. Every competing value, including the losers, is kept on the emitted `Conflict` with a resolution note. The e2e test verifies the career mixer resolves to the official 18:00 while the anchor-link 18:30 survives on the conflict row and the event reads `conflicting`.

Records whose `parse_status` isn't `ok` (the unparseable official page, E-11) are dropped from the field comparison rather than crashing the run, degrading to the remaining sources (AC-9).

### Food confirmation, RSVP health, cancellation

Event-level food confirmation is resolved by a dedicated `_resolve_food` rather than the generic cross-check: confirmed+contradicted → contradicted and flagged conflicting (E-5); confirmed+unmentioned → downgraded to unconfirmed (not falsely "verified"); all-confirmed stays confirmed. Because of this, `food_confirmed` is skipped in `_apply_field`, so its `FieldProvenance` is always `missing` even when sources agree — a cosmetic inconsistency, since the real decision is captured in the derived state and the `food_category` provenance is still recorded. Consider emitting a provenance row mirroring the food resolver.

RSVP link health is tri-state and considers *all* members (including a dropped source page whose own link is broken), so a broken RSVP link (E-8) flags `rsvp_link_ok=False` and feeds the ranking's rsvp_likelihood and the confidence blend. Cancellation from any contributing source sets `cancelled`, overrides every other state, and appends a single transition history entry; the orchestrator suppresses re-appending it when the previous stored state was already cancelled, so repeat runs keep exactly one cancellation row.

### Test coverage

93 tests pass with lint/format/type checks clean. The e2e suite asserts the four spec-named outcomes (pizza merge across anchor_link + google_calendar; career mixer → official 18:00 with 18:30 preserved and state conflicting; movie night cancelled; dinner > refreshments by score), plus idempotency across three runs and in-place time/venue updates with history. The web suite drives the Flask test client over a seeded in-memory repo and checks 200, ranked order (dinner before refreshments, pizza before cancelled movie), all required card fields, state badges, and the expandable conflicts section.

Not tested at the integration level: a live/online fetcher path (out of MVP scope by design), and the `possible_duplicate` borderline-merge flag surfacing in the UI (the flag is computed in dedup but the web card doesn't render it — acceptable for MVP, worth noting for M7+).
