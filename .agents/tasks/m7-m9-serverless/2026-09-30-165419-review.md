# Stateless-serverless conversion with Upstash snapshot store, Vercel Cron, Google Calendar write, and live Maps walking

This change reworks Vandy Food Radar from a SQLite-persistence + Render/APScheduler assumption into a stateless Vercel-serverless app whose only durable state is a per-target-date snapshot of the change-relevant event fields, kept in a free Upstash Redis instance (in-memory offline by default). On top of that seam it lands M7 (daily automation via a `/cron/refresh` route hit by Vercel Cron, plus a structured JSON run log and per-event change badges), M8 (an explicit, idempotent Google Calendar writer behind the existing `CalendarProvider`), and M9 (a live Google Maps walking provider behind `LocationProvider`, memoized with graceful fallback). Every external integration is behind an interface, disabled or faked offline by default, and the app boots and renders on Vercel with no env vars set. Watch for: nothing blocking — the store fails open to all-NEW on a KV outage (confirmed, intentional per the design), the calendar writer and maps provider never raise (confirmed), google libs are lazily imported so offline import stays clean (confirmed), and the 93 pre-existing tests are intact (confirmed, base=93 now=138).

**Verdict**: APPROVED

## High-level view

The storage seam is the load-bearing decision. SQLite stays exactly as-is for local/dev, and a new `SnapshotStore` protocol carries the only cross-invocation state — a JSON snapshot of eight change-relevant fields per target date. `run_with_snapshot` reuses the existing pipeline verbatim, then loads the previous snapshot, classifies changes, and re-saves. Both the Upstash REST implementation and the in-memory default round-trip through the same codec, so offline behavior matches production.

Failure posture is fail-open by design: any Upstash HTTP/JSON error makes `load` return `None` and `save` a no-op, which the change detector reads as "no previous snapshot" and therefore all-NEW. This is the correct trade-off for a change-annotation feature that must never break the page, and it is documented in the task.

Scheduling moved out of process entirely. There is no scheduler thread anywhere; `vercel.json` declares a daily cron on `/cron/refresh`, which runs the pipeline for tomorrow through `run_with_snapshot` and returns the run report plus change tally as JSON. The index view reads the snapshot read-only to attach change badges and never re-saves.

Calendar and maps are both interface-first and off by default. `GoogleCalendarWriter` writes only the one explicitly-POSTed event, is idempotent through a deterministic `iCalUID`, and reports errors instead of raising; its google-library imports are deferred into the builder so module import stays offline-clean. `GoogleMapsLocationProvider` memoizes by rounded coordinates and falls back maps→haversine→unknown, with unknown mapping to the neutral ranking value rather than zero.

The offline boot guarantee holds: `api/index.py` re-exports the WSGI app, `wsgi.build_app()` seeds the fixture corpus into an ephemeral `/tmp` SQLite db when the target day is empty, and `create_app` defaults every collaborator to its offline variant, so a fresh Vercel instance with zero env vars renders a populated page.

### The SnapshotStore seam replaces SQLite as the durable state

The architecture pivots on separating two kinds of state. Canonical event rows and scores still live in SQLite through the unchanged `SqliteRepository` (local/dev path, all its tests green). The only state that must survive between serverless invocations is the previous run's canonical events, and that is exactly what `SnapshotStore` holds — nothing more. The codec in `store/snapshot.py` serializes only the eight fields change detection actually reads (identity_key, title, event_date, start/end time, location, verification_state, score_total) with `sort_keys=True`, and decode rebuilds `Event` with every other field at its dataclass default. The stated hazard — a decoded snapshot event has `id=''` and must never be written back to SQLite — is respected: `run_with_snapshot` reads fresh events from the repository and only ever *saves* those to the snapshot, never the reverse.

```
                pipeline.run (unchanged)
                        |
   fresh = repo.get_events_for_day(target)
                        |
   previous = snapshot_store.load_snapshot(target)   <- Upstash GET or in-mem
                        |
   changes = detect_changes(fresh, previous)
                        |
   snapshot_store.save_snapshot(target, fresh)        <- Upstash SET or in-mem
```

`InMemorySnapshotStore` stores the encoded JSON string (not the live objects) and decodes on load, so its round-trip drops non-change fields identically to Upstash.

### Upstash REST over stdlib urllib, failing open on any outage

`UpstashSnapshotStore` talks to Upstash's REST API through a small injectable `SnapshotHttp` seam whose default uses `urllib.request` — no new runtime dependency for the store itself. The failure characterization is the important part: `load_snapshot` returns `None` on http-None, a null `result`, or any JSON/attribute/key error, and `save_snapshot` swallows everything. A KV outage therefore degrades to "no previous snapshot," which the detector treats as all-NEW rather than an error — fail-open, so a broken Redis annotates every event as new instead of blanking the page. `build_snapshot_store` returns the Upstash store only when both `UPSTASH_REDIS_REST_URL` and `UPSTASH_REDIS_REST_TOKEN` are non-empty (read as plain, non-`VFR_`-prefixed names because Upstash/Vercel set them), else the in-memory default. Tests inject a fake `SnapshotHttp` and assert the exact `["SET", "vfr:snapshot:<date>", <json>]` / `["GET", key]` commands and the `{"result": ...}` envelope decode, so no test touches the network.

### Change classification precedence

`detect_changes` is pure and deterministic. An identity_key absent from the previous snapshot is NEW; otherwise `_classify` applies CANCELLED (newly cancelled) > TIME_CHANGED (start or end differs) > VENUE_CHANGED (location differs) > UNCHANGED, and a `None`/empty previous makes everything NEW. The precedence ordering matches the spec's E-4/E-2/E-3/E-9 requirements, and the tally helper feeds the run-log counts. The one subtlety — a cancelled event whose time also changed must classify as CANCELLED, not TIME_CHANGED — is enforced by checking cancellation first and is covered by a dedicated test.

### /cron/refresh with no in-process scheduler

The `/cron/refresh` route (GET and POST) derives tomorrow's window, calls `run_with_snapshot`, and returns `run_report_to_json(report, changes)` as `application/json` 200. Scheduling is entirely external: a grep across the source for `APScheduler`/`BackgroundScheduler`/`scheduler`/`Thread(` finds only the test that asserts *absence* of those symbols and the docstring/comment stating Vercel Cron is the trigger. `vercel.json` declares `crons: [{ path: "/cron/refresh", schedule: "0 11 * * *" }]`. The index view attaches change badges by loading the snapshot and running `detect_changes` read-only — it never saves, so viewing the page can't perturb cross-run detection. Saving happens only in `/cron/refresh` (and `/refresh` via the pipeline).

### Explicit, idempotent Google Calendar writer

`GoogleCalendarWriter` sits behind the existing `CalendarProvider` protocol and only ever writes the single event whose `identity_key` was POSTed to `/calendar/add/<identity_key>`; the route skips cancelled events and there is no auto-add on render or GET. Idempotency comes from `iCalUID = "vfr-" + identity_key` sent to `events().import_()`, so a repeat add updates rather than duplicates (FR-40). `add_event` catches every exception and returns `CalendarWriteResult(ok=False, detail=...)` — it never raises into the request. The google client libraries are imported lazily inside `_build_google_service`, and this was verified empirically: after `import api.index`, neither `googleapiclient` nor `google.oauth2` is present in `sys.modules`. With the default Null provider the route flashes the graceful "Calendar not configured" message.

One behavior worth noting (not a defect): when `start_time` is present but `end_time` is not, the body sets end equal to start, producing a zero-length timed event; when there's no start time it falls back to an all-day entry. Both are reasonable and tested.

### Live Maps walking with memoization and neutral fallback

`GoogleMapsLocationProvider` implements `LocationProvider`, talks through an injectable `MapsHttp` seam (stdlib urllib default, no new dependency), and memoizes resolved `WalkingResult`s in an instance dict keyed on coordinates rounded to 5 decimals — a cache hit does not re-invoke HTTP, which the test verifies with a call-count assertion. The fallback chain is maps→haversine→unknown: a missing key, http `None`, non-`OK` Distance Matrix status, or any parse error delegates to the Haversine fallback. A missing `dest` yields `UNKNOWN`, and `walking_factor_value` maps `UNKNOWN` to `config.ranking.walking_unknown_value` (0.5) so an unknown walk never zeroes the ranking score (FR-30/AC-8). Default provider selection stays HAVERSINE; the live provider is chosen only when the kind is `GOOGLE_MAPS` and `maps.enabled` and an api_key is present.

### Offline boot on Vercel with no env vars

`api/index.py` is a thin `from vandy_food_radar.web.wsgi import app` re-export. `build_app()` reads `VFR_DB` (defaulting to `/tmp/store.db`, since Vercel's filesystem is read-only except `/tmp`), opens the SQLite connection with `check_same_thread=False` because a real WSGI server dispatches requests on worker threads distinct from the build thread, and seeds the fixture corpus once when the target day is empty (guarded so a populated store is never reseeded). `create_app` defaults `snapshot_store`, `calendar_provider`, and `location_provider` to their offline variants. The acceptance check — `import api.index; test_client().get('/')` with no env vars — returns 200 containing "Vandy Food Radar", confirmed independently here.

The `check_same_thread=False` addition to `SqliteRepository.__init__` is a keyword-only parameter defaulting to `True`, so every existing caller and test is unaffected; only `build_app()` opts in. This is the minimal backward-compatible fix for the cross-thread `ProgrammingError` a live server would otherwise hit.

### Packaging and deps

`requirements.txt` is committed (not gitignored — `.gitignore` covers `*.db`, `.env`, `uv.lock` only), includes flask + google-api-python-client + google-auth and transitive deps, and carries an `-e .` line so pip installs the package on Vercel. `vercel.json` pins `python@3.11` and rewrites `/(.*)` to the function so Flask serves its own static assets. The CLI `run` now emits the structured JSON run-log line after the human-readable summary with its subcommand surface (seed/run/--db) unchanged.

### Test coverage

45 new tests (base 93 → 138, all green under `make check` with mypy strict) cover the codec round-trip, in-memory and faked-Upstash store behavior including outage→None, change-detection precedence including the cancelled-and-time-changed case, snapshot-run NEW→UNCHANGED→TIME_CHANGED transitions, the cron route's JSON shape and idempotent repopulation, calendar body mapping / iCalUID idempotency / error path / build selection, and maps success/cache/fallback/neutral-value/build selection. Not tested (acceptably, since these are the un-fakeable network edges): the real urllib `SnapshotHttp`/`MapsHttp` transports and the lazily-built real Google service — all are exercised only through injected fakes, which is the correct boundary.
