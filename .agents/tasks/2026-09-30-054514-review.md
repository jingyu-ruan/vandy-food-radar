# Vandy Food Radar M1–M6: pipeline, ranking, and web UI

M1–M6 build out the full Discover → Normalize → Deduplicate → Verify → Rank → Display pipeline on top of the M0 foundation: a SQLite repository, offline source adapters, a pure normalizer + food classifier, deterministic dedup/merge, authority-precedence conflict resolution, the §6.1 weighted-sum ranker, and a server-rendered Flask UI. Everything is injected and offline by default, so the whole pipeline runs against the fixture corpus with no network. The build is green — ruff, black, and mypy pass, and all 90 tests pass including the e2e and web suites. The end-to-end fixture flow behaves as specified: the two pizza sources merge, the career mixer resolves to the official 18:00 with the 18:30 loser preserved and flagged conflicting, the cancelled movie night is marked cancelled, and the dinner-with-menu outranks the refreshments talk.

**Watch for:** re-run idempotency and change tracking are broken. The cancellation history entry is appended on every run rather than only on transition, so a repeated run accumulates duplicate history rows (confirmed — violates AC-10). And because `dedup_key` includes venue and rounded start time, a real time or venue change spawns a second event instead of updating in place with a history entry (confirmed — violates AC-11/E-2/E-3). Neither is caught by the current tests.

**Verdict**: NEEDS_CHANGES

## High-level view

The layering matches the design: sources, providers, and the HTTP fetcher are all constructor-injected, the web layer reads events/conflicts/sources through the `Repository`, and the default config runs offline. The one wrinkle is that the web view recomputes ranking at render time instead of reading the persisted score components.

Ranking is faithful to §6.1: the default weights match the spec table exactly (0.25/0.25/0.15/0.10/0.05/0.10/0.10, summing to 1.0), factors normalize to [0,1], each contribution is stored as a `ScoreComponent` with a note, and ordering is deterministic (cancelled last, score desc, earlier start, title). Unknown walking uses the configured neutral 0.5 and never zeroes the score.

Conflict resolution is correct and complete: per-field cross-check, authority precedence with a recency tie-break, and every losing value preserved on a `Conflict` row. The e2e test confirms the career-mixer case end to end.

The gap is in re-run behavior. Idempotent upsert by `dedup_key` works for an identical re-run (no duplicate events), but two change-tracking requirements are broken. Cancellation history is emitted unconditionally each run, and any change to a key-forming field (venue, or a start time that crosses the 30-minute rounding bucket) produces a brand-new event rather than an in-place update with history. The diff machinery itself works — it just never sees these changes because they land under a different key.

1. **Cancellation history duplicated on re-run** — `verify()` appends the `cancelled` history entry every run instead of only on the transition into cancelled; repeated runs accumulate duplicate history rows (violates AC-10/FR-42). Guard it against the stored state and assert history counts in the idempotency test.
2. **Time/venue change spawns a duplicate event** — `dedup_key` includes venue and rounded start time, so a start-time move across the bucket or a room change creates a new event instead of updating in place with old→new history (violates AC-11/E-2/E-3). Track the stored-event identity for updates on a key stable across these tracked changes.
3. **Web recomputes scores at render time** — `_build_cards` re-runs `score_event` instead of reading persisted `ScoreComponent` rows; wasteful and risks display/persistence drift. Render the stored components.

<summary>Details</summary>

### Web recomputes scores at render time

`_build_cards` recomputes `score_event` for every event on each render rather than reading the `ScoreComponent` rows the pipeline already persisted. The read-only-through-repository rule still holds for the data it displays, but scoring is duplicated work at display time and can drift from what was stored if the ranking config differs between the pipeline run and the render. Rendering the persisted components (and the explanation built from them) would keep display and storage in lockstep.

### Spec conformance confirmed on weights, ordering, and conflict resolution

`_default_ranking_weights` reproduces the §6.1 table verbatim (0.25/0.25/0.15/0.10/0.05/0.10/0.10, sum 1.0), each factor normalizes to [0,1] and is stored as a `ScoreComponent`, and `order_events` is cancelled-last then score desc then earlier start then title (§6.2). Unknown walking uses the configured 0.5 and never zeroes the score (FR-30/AC-8). Conflict resolution selects by authority rank, then most-recent `source_updated_at` (falling back to `checked_at`), preserving every losing value on the `Conflict` row (FR-18/FR-19); the e2e test confirms the career mixer resolves to the official 18:00 with 18:30 preserved and flagged `conflicting`.

### Re-run idempotency: cancellation history duplicated (confirmed)

`verify()` appends a `_cancellation_history` entry whenever the event is cancelled, with no check against whether the stored event was already cancelled. Running the pipeline over the unchanged corpus three times leaves three identical `verification_state -> cancelled` rows on the Outdoor Movie Night fixture:

```
run1 history_entries: 1   run2: 1   run3: 1
Outdoor Movie Night -> history rows in DB: 3
  [('verification_state', 'cancellation ...'), (x3)]
```

AC-10 requires that a repeated run over unchanged sources create no duplicate records *and no duplicate history entries*. The orchestrator's `_diff_history` correctly guards tracked-field changes (it returned 0 for unchanged fields across all three runs), but the cancellation entry bypasses that guard because it originates inside `verify()` unconditionally. The e2e idempotency test asserts only event count and source-record uniqueness, never history counts, so it stays green while the requirement is violated. The fix is to emit the cancellation entry only on the transition into cancelled — compare against `repository.find_by_dedup_key` the way `_diff_history` already does — and to add a history-count assertion to `test_repeat_run_is_idempotent_and_records_history`.

### Time and venue changes spawn duplicates instead of updating (confirmed)

`compute_dedup_key` builds the key from `event_date | title tokens | venue | rounded start time`. Because venue and start time are part of the key, changing either yields a *different* key, so the upsert inserts a second event rather than updating the existing one, and `_diff_history` never sees the change. Two runs where the only difference is the start time or the venue:

```
time 18:00 -> 19:00 :  event count 2   (two Talks, no history)
venue Hall A -> Hall B:  event count 2   (two Talks, no history)
within-bucket 18:00 -> 18:10:  event count 1, history: start_time 18:00:00 -> 18:10:00
```

The within-bucket case shows the update-and-history machinery works — it only fires when the change stays inside the same key. But AC-11 requires a start-time change to update in place and record an old→new history entry, and E-2/E-3 require the same for time and room/venue moves. T6.5 is tagged with AC-11/FR-43, so these are in scope. The design uses rounded-time + venue in the key for idempotency across identical re-runs, but that same composition makes the tracked changes indistinguishable from a new event. Resolving this needs a stored-event identity for update/history that is stable across the very fields AC-11/E-2/E-3 expect to change (e.g. reconcile an incoming event to an existing one on a coarser identity than the full dedup_key, then apply the diff), rather than keying idempotency on fields the spec expects to move.

### Test coverage

Strong per-module coverage: normalization (bad dates, vague food, missing fields), dedup (slight-name merge, same-time non-merge, recurring-across-days non-merge), conflict resolution (precedence, recency, losers preserved, official-page override), ranking (full-meal>refreshments, determinism, unknown-walking fallback), store round-trip and upsert, and the e2e + web flows. The fixture corpus is realistic and reused across suites.

**Not tested:** the number of history rows after a repeated run (would have caught the cancellation-history duplication), and the AC-11/E-2/E-3 change-tracking behavior — no test runs the pipeline twice with a changed start time or venue and asserts a single event updated in place with an old→new history entry. Both gaps correspond directly to the two confirmed defects above.
